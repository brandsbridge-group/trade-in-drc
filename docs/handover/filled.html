What is the application's current purpose, main user groups and critical business workflows?

TradeInDRC is a B2B trade portal for the DRC that connects Congolese exporters with international buyers. It runs on Next.js 16.1.1 and React 19 (App Router) with Supabase for Postgres, Auth and Storage, and every route lives under src/app/[locale]/. Five locales are live: English (the default), French, Turkish, Spanish and Chinese. They're listed in src/config/locales.ts, with the translated strings in src/config/messages/.

  • Roles are defined in src/lib/supabase/types.ts. ProfileRole is user or admin, AccountType is congolese_company or international_business, and StaffRole (added by migration 00013) is moderator or super_admin.
  • Public pages: /companies, /products, /services, /sectors, /market/[segment], /opportunities, /rfq, /data-hub, /news, /events, /blog, /trust/[companySlug], /request and /register-company, plus /search behind Cmd+K.
  • Dashboard sections: companies, products, services, rfq, opportunities, inbox, analytics, settings. Admin sections: verifications, companies, users, requests, content, taxonomy, data-hub, messages, analytics, settings.
  • Critical workflows: a company registers, then an admin verifies it, so CompanyStatus moves through pending, verified or rejected and VerificationTier through none, basic, verified or premium. Companies manage their listings and answer RFQs and opportunities in the inbox. Forms submitted at /request land in /admin/requests. I built the premium plans in src/config/promotion-plans.ts (congolese $3,000, international $3,600, and international_strategic; migrations 00038, 00039 and 00041) so an admin grants them at /admin/requests/premium.

Which backend framework, language, version and major libraries are used?

There's no separate backend service. There is no Node server framework, no ORM and no worker process. RLS in Postgres is the security boundary here, and an ORM sits in front of that boundary rather than behind it, so I kept the data access layer thin and let the database enforce the rules directly.

What database technology, version, ORM/data-access layer and schema migration tool are used?

The database is PostgreSQL hosted on Supabase, configured in supabase/config.toml with project_id = "tradeindrc" and local ports 54321, 54322 and 54323. The Postgres minor version is whatever the managed instance runs; it isn't pinned.

  • Data access: no ORM, on purpose. Queries go through @supabase/supabase-js v2, typed against src/lib/supabase/types.ts, a 1,876 line file maintained by hand. Do not run supabase gen types against it, that overwrites the hand-authored type aliases at the top of the file. When a migration changes the schema, edit the affected Row/Insert/Update fields by hand to match.

They're written to be idempotent, and the practice on this project is to apply each one to production as soon as it's written, with supabase db push or the Supabase MCP apply_migration call, rather than letting them queue up. Seed data is in supabase/seed.sql and apply_local_images.sql.
  • There are 46 tables and every one has RLS turned on: profiles, companies, the company_* tables (contacts, documents, media, references, segments, tags, hs_codes), products, services, sectors, categories, segments, tags, hs_codes, opportunities, opportunity_responses, opportunity_moderation_events, rfq_listings, business_requests, premium_requests, conversations, conversation_participants, messages, message_reports, verification_reviews, kyc_individuals, kyp_checks, reports, content_items, page_content, faqs, help_articles, carousel_slides, featured_companies, institutions, site_settings, contact_submissions, audit_log, analytics_events, market_metrics, price_points, price_series, trade_series and sector_activity.

That's Postgres doing the work a separate search service would otherwise do, and at this scale it's the right call.

5
What authentication and authorization model is used (roles, permissions, SSO, MFA, session management)?

Sign-in uses Supabase Auth (GoTrue) with email and password only. The signUp, signInWithPassword and resetPasswordForEmail calls are in src/components/auth/user-auth-form.tsx and (auth)/forgot-password/form.tsx, password re-authentication is in dashboard/settings/account/page.tsx, and the PKCE code exchange is in (auth)/callback/route.ts. RLS enforces email confirmation through public.is_email_verified(), added in migration 00003. SSO and MFA aren't implemented, since neither was in scope for this build, and both can be turned on in Supabase without a schema change when the new owner needs them.

Sessions are JWT access and refresh tokens held in cookies. updateSession() in src/lib/supabase/middleware.ts refreshes them on every request, called from src/proxy.ts. On the client, AuthProvider and useAuth() in src/lib/auth/auth-provider.tsx track the session with getSession() and onAuthStateChange.

Roles come from migration 00013_rbac_roles.sql and are mirrored in src/constants/roles.ts. Five roles exist:

  • Visitor has no row in profiles.
  • Congolese Company has account_type = 'congolese_company'.
  • International Business has account_type = 'international_business'.
  • Moderator has staff_role = 'moderator'.
  • Super-Admin has staff_role = 'super_admin'.

staff_role is the source of truth; the legacy profiles.role column is only a fallback. The SQL helpers are is_admin() from 00002, is_moderator() and is_super_admin() from 00013, and is_email_verified() from 00003.

Authorization is enforced in three layers. RLS on every table and on storage.objects is the real boundary, that's deliberate, everything above it is a convenience, not the guarantee. src/proxy.ts redirects requests that hit PROTECTED_ROUTES or ADMIN_ROUTES without the right session. requireAdmin(), requireAuth() and requireCallerAdmin() in src/lib/auth/ guard server code, and require-admin.test.ts covers the unauthenticated, unauthorized and infrastructure-failure cases.

Migration 00037_profiles_privilege_lockdown.sql closed a privilege-escalation hole found during development. Table-wide UPDATE was revoked from authenticated and anon and re-granted column by column for full_name and avatar_url, and INSERT and DELETE were revoked from anon. The role, staff_role and account_type columns are now writable only by the service-role key. The audit_log table from migration 00015 records privileged actions, worth checking periodically once the platform has real usage.

Turnstile blocks abuse on message sends and opportunity submissions. It calls https://challenges.cloudflare.com/turnstile/v0/siteverify with CAPTCHA_SECRET_KEY and NEXT_PUBLIC_CAPTCHA_SITE_KEY.   • The other checks are npm run lint, npm run build and npm run check:i18n.

Those four commands are the quality gate. I ran them through an agentic workflow rather than a hosted pipeline, because one engineer was committing and the repo carries a strong convention layer for an agent to work against: a root CLAUDE.md, seven folder-level CLAUDE.md files, and docs/MOTION.md, spelling out the architecture rules, the Supabase client rules, the migration rules and the motion rules. An agent reads those, makes the change, and runs lint, test, build and check:i18n before the code lands. The checks run on every change, enforced by the agent and the conventions rather than by a server. There's no coverage provider or threshold configured, and no end-to-end or visual regression tests. Once more than one person is committing, stand up a hosted CI pipeline running these same four commands against every PR — that's the natural next step for a multi-engineer team.

What browsers, devices and accessibility requirements are supported?
  • Browsers: there's no browserslist and no target override in next.config.ts, so the app targets the Next.js 16.1.1 default of modern evergreen browsers (Chrome, Edge, Safari, Firefox). Legacy browsers are untested. Linting uses eslint-config-next/core-web-vitals, but Core Web Vitals aren't measured.
  • Devices: layouts are responsive through Tailwind v4 and shadcn/ui, with a mobile nav in src/components/layout/mega-menu.tsx. There's no device matrix and no cross-browser testing service in the loop.
  • Accessibility is built in at several points: a reduced-motion block at src/app/globals.css lines 186-193, useReducedMotion() in 14 files, the rules in docs/MOTION.md sections 4 and 7, Radix primitives, 77 aria-label attributes, 8 sr-only elements, and <html lang={locale}> at src/app/[locale]/layout.tsx line 92.
  • A WCAG 2.1 AA conformance statement, an automated accessibility scan (axe or pa11y) and a skip-to-content link are not in place yet. If accessibility conformance becomes a contractual requirement, that's the order I'd add them in.

What are the current defects, known limitations, performance bottlenecks and priority backlog items?
  • Quality gating is agent-driven, not pipeline-driven (see the answer above). Lint, test, build and check:i18n run before code lands, but nothing enforces that server-side yet.
  • Translations cover 5 locales (en, fr, tr, es, zh) with 3,534 keys each, but scripts/check-i18n.js only compares English against French, so TR, ES and ZH are unverified. EN and FR are clean apart from 208 English keys that look unused.

Worth a cleanup pass before anyone relies on them.
  • Roadmap work still open in docs/superpowers/specs/2026-05-17-master-roadmap-design.md: slice S6 Data Hub is partial (prices and reports exist, the legal library doesn't), and S8 and S9 are untouched. Payments and escrow, and realtime notifications, were scoped out as non-goals for this build, not deferred by accident.
  • There's no transactional email dependency; the app relies on Supabase Auth mail for that, by design.
  • Test depth is thin by intent, not oversight, for a single-engineer build: 58 unit tests, no end-to-end tests, no profiling or Lighthouse budget, and no error tracking wired in. These are the natural next investments as the team and traffic grow.
