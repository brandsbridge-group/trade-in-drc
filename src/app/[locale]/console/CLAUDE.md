# Staff console rules (`/console`)

- This is the **staff** back-office (Super Admin + Moderator). It was called `/admin` until 2026-09-30; old URLs 308-redirect here (`next.config.ts`). In product language "Admin" now means a **company owner** in `/dashboard` — never call this area "admin" in new copy or routes. Full role/route model: `docs/context/roles-and-access.md`.
- Every page is server-guarded via the parent `layout.tsx` (`requireStaff()` in `src/lib/auth/require-admin.ts`). Do NOT skip the guard, even for "internal" tools.
- Sections that grant privilege or change platform settings are **super-admin only**: list them in `SUPER_ADMIN_ROUTES` (`src/constants/routes.ts`) AND guard their server actions with `requireSuperAdmin()`, not `requireAdmin()`. The proxy and sidebar read the same list.
- Link with `ROUTES.CONSOLE*` constants, not string literals.
- RLS is the source of truth for authorization. Frontend guards are UX only — assume the layout guard could be bypassed and write queries that fail safely under user RLS.
- NEVER import `src/lib/supabase/admin.ts` (service-role client) into any client component or any file that gets shipped to the browser. Service-role bypasses RLS.
- All console copy must be translated via next-intl (the message namespace is still `Admin.*`). No hardcoded strings.
- Pages follow shadcn + compact, dense layout (see project memory: minimal padding, brand-color CTAs).
- **Visual language (2026-10-01):** same as the company dashboard (`dashboard/CLAUDE.md`) — `bg-slate-100` canvas, white `rounded-2xl ring-1 ring-slate-200/70` cards, white sidebar with a navy pill on the selected item. The shell lives in `src/components/console/` (`sidebar.tsx`, `topbar.tsx`, `nav-config.ts`); add a section to `CONSOLE_NAV` there, in the right group, never in the layout.
- The layout provides the page padding and max width: a page root is `<div className="space-y-4">`, never `p-4`. Use `PageHeader` from `@/components/console/page-header` (not the public one in `components/design`).
- Tables go inside `<div className="console-table-card">` (white card, slate-50 rounded header, horizontal scroll on phones). shadcn `<Card>` is restyled automatically under `.console-surface` (both in `globals.css`). Statuses are a coloured dot + label pill, primary CTAs a navy pill (`bg-market-navy … rounded-full`), sub-navigation a segmented control (see `content-tabs-nav.tsx`).
- KPI rows reuse `KpiTile` / `OverviewCard` from `src/components/dashboard/overview/`, with one `highlight` tile per row.
- **Console home (`page.tsx`, 2026-10-02):** every number comes from the `console_dashboard_metrics(p_days)` RPC (00059, `is_admin()` only) via `src/lib/console/dashboard-metrics.ts` — never count `companies` or `analytics_events` rows in the browser (1000-row cap, and `analytics_events` RLS only lets legacy `role = 'admin'` through). To add an indicator, extend the function in a new migration and the `ConsoleDashboardMetrics` type. Cards live in `src/components/console/dashboard/`; charts reuse `ActivityChart` and `BarList` with the validated `SERIES_COLOR` pair (blue, hatched gold) — one colour per series, no new hues.
- **Specification templates (`/console/taxonomy`, `SpecFieldsEditor`):** per category, the fields sellers fill in the product form (`category_spec_fields`, 00055). The `key` is derived once from the English label and never edited — products store their values under it; a select option keeps its `value` when its label is renamed. Deleting a field does not delete product values: they fall back to free lines.
- **Verification circuit (`/console/verifications`):** `companies.status` alone does not say whose turn it is — after "request more information" the company stays `pending`. Always derive the stage with `reviewStage()` (`src/lib/verifications/workflow.ts`, unit-tested): `to_review` vs `awaiting_owner` comes from the LAST `verification_reviews` event. Every send and every decision writes an event (`submitted`, `resubmitted`, `approved`, `rejected`, `more_info_requested`); the submission date and waiting time are read from that trail, never from `created_at`. Staff decisions go through `submitVerificationDecision` (approving an incomplete file needs `overrideMissing`), a single document through `setCompanyDocumentStatus`, the public trust checks through `saveTrustProfile` — which MERGES into `verification_summary`; never write that column from the browser, it also holds the company's `registration_intake`.
- **Staff checks in SQL:** always `public.is_admin()`, never `profiles.role = 'admin'` — staff accounts carry `staff_role`, not the legacy role (22 old policies were fixed in 00060).
- **Requests addressed to a company (`/console/requests`, 00062):** a quote request (product page) or a contact request (company page) carries `target_company_id` (+ `product_id`, `quantity`, `interest`), and its `message` holds the buyer's own words only. `company_id` is NOT the target — some forms fill it with the requester's own company. The company sees nothing until staff forwards the request with `forwardBusinessRequest` (sets `forwarded_at`, moves `new` to `in_progress`); forwarding exposes the buyer's contact details, so it stays an explicit, confirmed action. A new form aimed at one company must set `target_company_id` and call `recordContactRequest()` (`src/lib/analytics/contact-request.ts`). The screen is KPI tiles → quick views with counts → filters as removable chips → table whose rows open a side panel (`RequestDetailSheet`, never a dialog); the tiles and the quick views share the counting rules of `src/lib/requests/views.ts` (unit-tested) — add a view there, not as a second filter in the component.
- **Form answers and attached documents (00065):** `business_requests.details` holds what a form asked beyond the shared columns, as KEYS the panel translates (the partner form of `/request`: need, product, volume, preferences, website — read it with `readPartnerRequestDetails()`, `src/lib/requests/partner-request.ts`; `timeline` is a key too for that form). Never store a translated label or fold answers into `message`: staff filters break per language. An attached document lives in the private `request-attachments` bucket, which has NO storage policy on purpose: the visitor uploads through a one-time signed upload URL, staff downloads through `getRequestAttachmentUrl()` (5-minute signed link). The path never goes to the browser — rows carry `has_attachment` only.
- **Following a request (`/request/track`):** reference + e-mail, through `trackRequest()` (`src/lib/requests/track-actions.ts`, service role). References are sequential, so the e-mail must match and a wrong pair answers exactly like an unknown reference. Only `buildTracking()`'s steps leave the server — never `admin_notes`, `follow_up_owner` or the raw status.
