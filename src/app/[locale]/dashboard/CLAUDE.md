# User dashboard rules

- All dashboard pages assume an authenticated session. Use `useAuth()` from `@/lib/auth/auth-provider` on the client; on the server use `createServerSupabaseClient()` from `@/lib/supabase/server`.
- Server state: React Query. Client state: Zustand. Do not invent new stores.
- Show optimistic UI for toggle-style mutations; use `toast.loading` → `toast.success/error` for long-running ones (NON_BLOCKING_UX).
- Unverified-email users see an amber banner on settings; sensitive mutations are blocked at the DB level by `is_email_verified()` (migration 00003).
- **Analytics: never query `analytics_events` from the dashboard.** Owners have no SELECT policy on it (admin-only, 00001), so a direct read silently returns 0 rows. Every count, trend, daily series, top product and search entry comes from the `owner_dashboard_metrics(p_days)` SECURITY DEFINER aggregate (migration 00052) via `fetchOwnerDashboardMetrics()` in `src/lib/dashboard/overview/metrics.ts`. Need a new metric? Add it to that function (new migration), not a client query.
- **Statistics (`analytics/page.tsx`, 2026-10-05):** same building blocks for every account, ordered and worded by account type — a Congolese company reads how buyers find and contact it, an international one reads its prospecting in the DRC, no company sees an invitation to register. It adds `owner_analytics_details(p_days)` (00067, `src/lib/dashboard/analytics/details.ts`) to the home aggregate: unique visitors, the owner's own reply time, forwarded requests, catalogue health, opportunities, and figures company by company when the owner has several. Blocks live in `src/components/dashboard/analytics/stat-blocks.tsx`; copy in the `OwnerStats` namespace. The navy `StatsHero` band is the page's one featured surface, so its KPI tiles stay white.
- **Home page (`page.tsx`) structure** follows the 2026-09-30 report (`docs/reports/`): "À faire maintenant" → 4 KPI tiles (period 7/30/90 d vs previous period) → results cards. It adapts to the account type — Congolese (a company in the DRC) sees buyer interest; international sees DRC opportunities, replies, suppliers and market watch; no company yet sees the guided onboarding. Components live in `src/components/dashboard/overview/`, pure rules in `src/lib/dashboard/overview/` (tasks, profile completeness, trends — unit-tested in `overview.test.ts`). Copy lives in the `DashboardOverview` namespace.
- **Getting-started guide:** `buildOnboarding()` (`src/lib/dashboard/overview/onboarding.ts`, unit-tested) computes the four steps from real data — account → company → documents sent (status `pending`/`verified`) → first product. `OnboardingGuide` renders it as the whole home (`welcome`, no company) or as a card above the KPIs (`progress`), and disappears once every step is done. Add a step there, never as a hard-coded list in a component.
- **Company registration (`companies/new`):** dashboard-only since 2026-10-01. The wizard (`src/components/register/market/`) is rendered here in the dashboard's visual language; the public `/register-company` only redirects (signed in → here, visitor → `/signup` then back here). Link to `/dashboard/companies/new` from inside the dashboard; public CTAs keep `/register-company`.
- **Profile editor (`companies/[id]/edit`):** four blocks with anchors (`#presentation`, `#commerce`, `#contact`, `#media`), each with its own "n/total" pill and its own Save (media saves itself). `COMPLETENESS_SECTION` / `completenessHref()` in `profile-completeness.ts` map every completeness criterion to its block; the home's "complete your profile" row and the editor's header chips both use it — add a criterion there, not a hard-coded link. `companies.description` is the public pitch only: never append internal notes to it.
- **Legal identifiers** (RCCM / registration number, NIF, national ID, legal form, year, headcount) are edited on the verification screen and stored in `verification_summary.registration_intake.legal` through `saveCompanyLegalIdentity()` (service role after an ownership check — owners cannot write that column). The registration number, plus the NIF for a DRC company, are required before review.
- **Verification (`companies/[id]/verification`):** the only way out of `pending_documents`. The owner uploads through `uploadCompanyDocument()` (browser client, RLS) and sends with `submitCompanyForReview()` (`src/lib/verifications/owner-actions.ts`), which checks ownership and the required documents (`required-documents.ts`: RCCM + NIF for a DRC company, registration certificate only otherwise) before the service-role write of `status = pending`. Owners can never write `companies.status` directly.
- Search query text is **not stored** (analytics_events keeps only the entity that surfaced), so never promise "keywords" — show what buyers found (entities), as the home and Statistics pages do.
- The layout is responsive: `Sidebar` is desktop-only (md+), `MobileDashboardBar` opens the same nav in a drawer on phones. Keep `min-w-0` on `<main>` so wide tables can't push the page sideways, and give every CSS grid explicit columns (`grid-cols-1` on mobile) plus `min-w-0` on its children — an implicit grid column grows to its content and overflows phones.
- **Visual language (2026-09-30 premium redesign):** soft `bg-slate-100` canvas, white cards `rounded-2xl ring-1 ring-slate-200/70` (depth from contrast, no `shadow-*`), **white** sidebar panel floating on the canvas, with navy reserved for the selected item (`bg-market-navy` pill, white text) and the subscription-upgrade card (gold only on its button), one featured navy tile per row of KPIs, icon chips `rounded-full bg-slate-100`, statuses as coloured dot + label, table headers `bg-slate-50` rounded. Nav items/groups live in `src/components/dashboard/nav-config.ts`; the awaiting-replies count comes from `useAwaitingReplies` (shared by rail badge, top bar and overview).
- **Chart colours:** series use `#24508F` (lifted navy) and `#B68B3A` (`market-or-dark`), validated with the dataviz palette script. Never plot in raw `#0B1F3A` — it reads as black and fails the lightness band. The second series is hatched so it is readable without colour.
- **Product editor (`ProductForm`):** one language tab at a time; `resolveProductTexts()` (`src/lib/dashboard/product-texts.ts`, unit-tested) requires a name and a description in at least one language and mirrors the missing one. A product is always saved but is public only when its company is `verified` (RLS `products_public_read_verified_company`) — the form's visibility card states it; do not add a second, client-side gate that blocks saving.
- **Product specifications:** `products.specs` stays one flat `{ key: value }` object. Template fields of the product's category (`category_spec_fields`, 00055, managed by staff in `/console/taxonomy`) are stored under their `key` — numbers raw (the unit lives on the template), booleans as booleans, a select as its option `value`; the seller's free lines are stored under the label they typed. All reading and writing goes through `src/lib/products/specs.ts` (`specEntries`, `splitSpecs`, `buildSpecs`, `rebaseSpecs`, unit-tested) — the form, the console and the marketplace share it. A field's `key` is permanent once created; only labels change.
- **Product price and minimum order (00064):** four optional columns — `price` (for ONE `sale_unit`), `price_currency` (USD / EUR / CDF), `sale_unit` (a key: kg, tonne, bag…; labels in the `ProductPricing` messages) and `min_order_quantity` (counted in the same unit). A figure without its unit is refused by the form and by a CHECK. All parsing, validation and printing goes through `src/lib/products/pricing.ts` (`buildPricing`, `pricingOf`, `pricingDisplay`, unit-tested), shared by the form, the dashboard and the public card / offer page. Empty = "price on request"; a product's own minimum order replaces the company-wide `companies.moq` wherever both could show.
- **Products pages:** `products/page.tsx` (catalogue: figures, search / category / status filters, sort, cards or rows), `products/[id]/page.tsx` (seller's detail: photos, texts, characteristics, status, views, listing quality) and `products/[id]/edit`. Rules live in `src/lib/dashboard/products.ts` (`productVisibility`, `productQuality`, `filterProducts`, unit-tested); the per-product actions (edit, duplicate, hide/show, delete behind a confirmation) are the shared `ProductActionsMenu`. Per-product views come from the `owner_product_metrics(p_days)` aggregate (00057) — same reason as the analytics rule above. A product is public when its company is verified AND `products.is_published` is true (RLS, 00057): to take a product offline, flip that flag, never delete.
- **Unsaved edits are kept locally.** A dashboard form with an explicit Save keeps its unsaved changes in `localStorage` through `src/lib/drafts/local-draft.ts` (`changedFields` → `writeLocalDraft`, restored with `applyDraft`), stores only the fields that differ from the saved values, shows a "restored" banner with a discard button, and removes the draft once everything is saved. Never write the draft before the stored values are loaded (an empty form would wipe it). Used by the company editor, the legal identity card and the company creation wizard (its own key in `register-wizard.tsx`).
- **Received requests (`requests/page.tsx`):** buyer quote/contact requests reach the company only after staff forwarded them (00062). Owners have no SELECT on `business_requests` (staff notes live there): read through `company_received_requests()` and mark as opened with `mark_received_requests_seen()`, both via `src/lib/dashboard/received-requests.ts`. `useReceivedRequests` is the single cache behind the page, the sidebar badge and the home's `requests_received` task. A company publishes its OWN offers and demands as opportunities (`opportunities/`): the old `rfq/` section ("Demandes de devis") was retired on 2026-10-03 — its announcements went to `rfq_listings`, which no public page shows — and both `rfq` routes now redirect to `/dashboard/opportunities/new`. Do not bring it back in the menu. The screen is a mail-style inbox (`src/components/dashboard/requests/request-inbox.tsx`): tabs with counts and search, list on the left, selected request on the right, one pane at a time on phones. Tabs and search are the pure `filterReceivedRequests()`; the "New" tab uses the ids that were unopened when the page loaded, because opening the page marks everything as seen.
- **Direct messaging is switched off (2026-10-05):** `MESSAGING_ENABLED` in `src/config/features.ts` (env `NEXT_PUBLIC_MESSAGING_ENABLED`, off unless `true`). Off, a buyer and a company never write to each other: every contact goes through the team (`/console/requests`). The switch hides the inbox (menu, top bar, account menu, home shortcuts; `inbox/layout.tsx` redirects), the "message the supplier" buttons of product and provider pages, and the reply/contact actions of a notice — and `startConversation`, `sendMessage` and `insertOpportunityResponse` refuse on the server. Any NEW way for a buyer and a company to write to each other must read the same constant on both sides (screen and server action). Nothing is deleted while it is off. The console's message moderation is untouched.
